# 执行期裁定记录（upstream-sync 机制）

本文件是本次建设的**决策记录**：执行过程中由控制器替人做出的每一处判断，按时间顺序列出。
它回答的问题是"为什么最终形态是这样，而不是计划里写的那样"——计划（`docs/local/plans/`）是
设计的骨架，本文件是骨架被现实修正的过程。

- 生成方式：从执行 ledger（SDD 工作区，`.superpowers/`，收尾时删除）逐条提取。
- 净化：提取时已把被泛化的标识替换为占位符（`<app-package>`、`<target-app>`、`<device-model>`），
  并通过本仓库自己的敏感信息闸门校验。
- 相关文档：设计 spec（`docs/local/specs/`）、实施计划（`docs/local/plans/`，末尾含"实施与计划的差异"）。

## 一、按主题的分类摘要

| 主题 | 关键裁定 |
|---|---|
| 拓扑与分支 | `main` 只作镜像 ref（永不 checkout）；`local` 为永久工作分支；不建 worktree（软链接指向主工作区） |
| 审批凭证 | `PLAN_ID` 绑定**内容**而非仅状态（未跟踪技能逐文件摘要）；单次计算；git 配置无关（quotePath/autocrlf/untrackedFiles 全部强制）；拒绝时不留下"像凭证的工件" |
| 闸门语义 | `--staged` 读**索引** blob；`--range` 扫**范围内新引入的全部 blob**（按对象寻址 + 全名清单）；`--paths` 扫文件系统；规则表不可用/空表/坏正则一律 fail closed |
| 内容卫生 | 净化标准以**用户要求**为准，不以规则表为准（规则表是下限）；"加完再删"、"文件名类规则"、"目录误报"三类盲区各自闭合；构建产物（`.pyc`）会夹带绝对路径 |
| 推送安全 | 读**全部** pushurl 并逐条比对；`upstream` 的 push URL 置为不可用值；`.sync/` 永不入库或推送；提交身份只报告不判断 |
| 退出码 | `2` = 用法/分支/调用方数据问题，`1` = 运行期错误，`3`/`4`/`5`/`6`/`7` 各自的拒绝含义 |
| 自检 | graphviz / ShellCheck 缺失时**条件纳入并响亮提示**，绝不静默；套件尾部与 harness 自检强制 |
| 文档诚实性 | 文档与**运行时输出**都不得声称机制未做到的事（符号链接前提、运行时可见性、只读性、恢复建议） |
| 过程方法 | 任何承载结论的检查必须附**正向对照**；夹具字节必须唯一（否则按对象枚举不列它）；变异验证优先于"看起来对" |

## 二、逐条裁定（按时间顺序）

  | T1 | 仅 git 状态操作，无文件；I1 验证依赖 `upstream/main` 引用 | **发现缺陷 → 见 Ruling R2** |
  | T2 | 测试断言 vs 库函数；I2 早期为空集导致断言恒真 | 一致，但见 Ruling R5 |
  | T11 | 九项验证；默认自检含 graphviz 依赖测试 | **发现缺陷 → 见 Ruling R3** |
  - **Ruling R1**：不创建 worktree。隔离机制 = `local` 分支 + 主工作区永久 checkout（spec §2 D2 与 §4 A 明确要求），再开 worktree 会让 `~/.dsh/skills` 软链接指向错误的工作树。代价：若将来需要并行工作，需重新审视软链接指向。
  - **Ruling R2**：Task 1 除 `git fetch upstream main:main` 外，**必须**再执行一次默认 refspec 的 `git fetch upstream`，使 `refs/remotes/upstream/main` 存在。原因：spec 定义 I1 为 `git rev-parse main` == `git rev-parse upstream/main`，而命令行 refspec 不会创建远端跟踪引用；不改则 T2 的 I1 断言会退化成"main 与 main 比较"而恒真。代价：无（纯增益）。
  - **Ruling R3**：apply 的默认自检对 graphviz 依赖测试改为**条件启用**（`command -v dot` 成功才跑 `tests/writing-skills/test-render-graphs.sh`），与 ShellCheck 的处理方式对称；跳过时必须**打印醒目提示**，不得静默。原因：本机未装 graphviz，该测试当前 exit 1，若无条件纳入则 apply 永远以 exit 6 拒绝推送。代价：render-graphs 相关回归不会被本地闸门捕捉（该路径与本机制新增文件无关，且本机无法验证）。缓解：T11 与 T12 的汇报必须写明该限制，不得声称"全绿"。
  - **Ruling R5**：`docs/local/**` 在 Task 11 之前是未跟踪文件，因此 I2（`main...local` 全为 A）在早期阶段恒真；有意义的 I2 校验发生在 T11 Step 4 与各 scratch 仓库测试中。代价：早期的 I2"通过"读数不具备证明力。
  - **Ruling R6**：D8 宣布接受身份邮箱只适用于**提交元数据**；扫描器仍拦截**文件内容**中的邮箱（两个不同暴露面）。若用户要放宽内容侧，需显式提出。
    1. **计划缺陷（Ruling R7）**：`git fetch upstream main:main` 在 `main` 处于 checkout 状态时被 git 拒绝（git 不允许 fetch 进当前已检出的分支）。子代理正确报错并按我的指示"先问不要擅自改"，于是阻塞等待 —— 而子代理的问题**只在它结束/被中断后才送达控制器**，因此空等了 71 分钟。
    2. **网络出口不通（Ruling R9）**：此刻到 github.com 的 TCP 连接超时（DNS 正常）。
  - **Ruling R7**：Task 1 的正确顺序是 —— unshallow → 加 upstream remote → 禁用 push → **先 `git switch -c local`** → 才更新镜像 ref。理由：`git fetch <remote> <br>:<br>` 拒绝更新已检出的分支。代价：无（顺序调整，语义不变）；spec §4 的 M1/M2 描述顺序需按此理解（M1 中的镜像 ref 更新必须发生在 M2 之后）。
  - **Ruling R7b**：本任务**跳过**那次镜像 ref 更新 —— 实测 `main` 已等于 `upstream/main`（均为 bb92a77），该 fetch 是 no-op，且当前无网络。代价：镜像 ref 的更新路径要等首次真实同步（`plan.sh`）时才被验证。
  - **Ruling R8**：后续所有 implementer dispatch 一律加入 —— **不得因提问而阻塞**：把问题写进报告文件，先完成不受阻塞的部分，以 NEEDS_CONTEXT 返回并把问题放在最终消息里。
  - **Ruling R9**：网络出口当前不通。T2–T10 全部可离线完成（其测试用本地 bare 仓库，不依赖网络）；T11 的 I1 活体校验改为**以本地 `upstream/main` 引用为准**，活体 `ls-remote` 作为可选交叉校验，不通时标注为"跳过"而非失败；T12 的首次 push 需要网络，届时若仍不通，改为向用户报告阻塞而不是伪造成功。
  - **Ruling R10**：Task 1 无文件改动、无提交（diff 为空），因此以**控制器的独立状态核验**替代逐任务 review（review 门针对的是落地代码；空 diff 无可审对象）。核验为我自己执行、非引用子代理报告：分支=local、`main`==`upstream/main`==bb92a77、`MIRROR_IS_ANCESTOR`、684 提交且 `.git/shallow` 不存在、`upstream` pushurl=DISABLED-no-push、`main..local`=0、工作区仅 `?? docs/local/`。代价：若将来有人改回 `main` 上的状态，本任务没有 review 记录可追溯（由 T2 的 I1/I2 测试兜住）。
  - **Ruling R11**：子代理报告的"brief 预期 `?? .superpowers/` 有误"成立（`.superpowers/` 确实被 .gitignore 忽略）。不计为缺陷，属于 brief 的预测偏差；已在本 ledger 记录，不修改计划正文。
  - **Ruling R12（接受实现者的偏差）**：`"$b，"` → `"${b}，"` 是必需的。我独立复现：缺 `${}` 时输出 `当前分支为 ??必须在 local 上操作`（分支名被吞），`set -u` 下报 `b?: unbound variable`。属 Global Constraint 1（bash 3.2 兼容）强制要求。已回写计划并加注该陷阱全文仅一处（`LC_ALL=C grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[^ -~]'` 核验：计划 1 处已修、实现 0 处）。
  - **Ruling R13（接受 Finding 1）**：`sync_conflict_preflight` 必须加 `--no-messages`。我独立复现：`--write-tree --name-only` 的两行提示（`Auto-merging …` / `CONFLICT …`）在 **stdout**（`1>/dev/null` 时 stderr 为空），故 `2>/dev/null` 压不住，一个冲突会返回 3 行，污染状态哈希、plan 报告与 apply 的 REFUSED 文本。已回写计划。

  - **Ruling R16**：计划 Task 3 的"替换占位实现"措辞已改为"新增"（占位在计划自查阶段就删掉了，属陈旧文本）。
  - **Ruling R17**：为 `sync_conflict_preflight` 的契约补一条 scratch 断言（恰好一行且等于冲突路径）。原计划没有任何测试守住这条契约，而它有三个消费方。
  - **Ruling R18（接受实现者对 F2 的细化，且实测复现）**：保留 `|| true`，只删死变量。我独立复现：`bash -c 'set -euo pipefail; f(){ local out; out="$(false)"; printf PRINTED; }; f'` → rc=1 且 PRINTED 不输出；加 `|| true` 后正常。结论：我原指示里"连 rc 记账一起删掉"是错的，删掉会让 `CONFLICTS="$(sync_conflict_preflight)"` 在有冲突时返回**空**，导致 T5 报告"无冲突"、T6 不以 exit 7 拒绝 —— 审批门静默失效。已实现为 `... 2>/dev/null) || true` 并附注释。代价：无（已实测）。

  - **Ruling R20（更正记录：我 R18 的理由错了，结论仍成立）**：实现者指出——在 bash 3.2 上，`CONFLICTS="$(sync_conflict_preflight)"` 这一形态**不会**因 merge-tree 的退出码 1 而变空（赋值里的命令替换屏蔽了 `set -e`）。我独立复现：直接调用 → rc 1 且中断；`x="$(f)"` → rc 0 且跑完。故 R18 中"删掉保护会让 T5/T6 静默失效"的说法**不成立**，但 `|| true` 依然是对的：它保护的是直接调用/管道形态，并对更新版 bash 的 `-e` 传播更严格这一前景留出余量。代价：若将来有人把 T5/T6 的调用改写成裸调用，保护仍在（已由 G1/G2a 断言锁定）。
