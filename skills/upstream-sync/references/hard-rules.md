# 硬规则与保证边界（Hard Rules）

`skills/upstream-sync/` 的机制围绕下面这几条来设计。凡是"机制能强制"的，脚本会拦住；凡是靠约定的，本文件写明它是约定 —— 不要把约定读成保证。

## 推送原则

**任何推送到远端的内容，都不得包含 API key、访问令牌、口令等凭据，也不得包含个人身份信息与个人环境信息。** 命中即硬失败，不做"看起来不像真的所以放过"的判断。这是人类伙伴的明确要求，也是整套闸门存在的理由。

命中的处理只有三条路：**改写（首选）**、移出仓库、**由本人**写入白名单。白名单文件 `.sync/allowlist.txt` 每行 `rule-id<TAB>仓库相对路径<TAB>原因`，只豁免前两字段完全相同的那一对；该文件本地留存、**不入库、不推送**，且**禁止**记录原文片段。

## 八条硬规则

| # | 规则 | 机制上靠什么强制 |
|---|---|---|
| 1 | `upstream` 的 push URL 不可用 → 误推 upstream 不可能发生 | 该 URL 就是禁用标记；`apply.sh` 推送前逐条检查，不等即 exit 5 |
| 2 | 永不 `git push origin main`；永不 checkout `main`；永不在 `main` 上提交 | 分支守卫要求当前分支是 `local`，否则 exit 2；两个脚本都不 checkout 任何分支，`main` 只作为 ref 被 fetch 与 merge |
| 3 | 永不运行 `scripts/bump-version.sh`，版本号一律跟随 upstream | 约定（脚本不拦）；版本号出现在 plan 报告的"上游版本"一行，也以 `upstream_version` 写进 `.sync/plan.json` |
| 4 | 永不修改 upstream 拥有的文件 | I2 校验：`main...local` 的每一行状态必须是 `A`，否则 plan 打印 `REFUSED` 并 exit 2 |
| 5 | 不向上游开 PR、不提 issue | 约定（AGENTS.md 也明确 fork 定制 PR 会被关闭） |
| 6 | 自定义内容只落在 `skills/<新目录>/` 与 `docs/local/` | `apply --adopt` 只 `git add skills/<name>`；`docs/local/` 由本人提交 |
| 7 | 未获明确同意，不执行 merge、不执行 push | `apply.sh` 必须拿到与当前状态匹配的 `PLAN_ID`，否则 exit 3；`plan.sh` 不碰工作区、索引与分支（它确实会拉镜像 ref，并写 `.sync/plan.json` 与 `.git/info/exclude`） |
| 8 | 未经敏感信息扫描通过，不执行 push；白名单只能由本人添加条目 | 三道闸门 G1（plan 的 `--range main...local`）、G2（apply 的 `--staged`）、G3（apply 的 `--range <推送范围>`） |

## `upstream` 的 push URL 是禁用标记

```bash
git remote get-url --all --push upstream     # DISABLED-no-push
```

- 上游 URL 不是仓库地址，`git push upstream …` 在物理上推不出去 —— 这不是"靠纪律"，是配置事实。
- `apply.sh` 里那个常量是唯一出处；检查覆盖 `upstream` 的**每一条** push URL（一个 remote 可以配多条）。
- 这条检查与 `--no-push` 无关：它校验的是配置不变量，不是"这次要不要推"。

## 保证与边界

每条保证后面都跟着它的边界。**边界不是免责声明，是这套机制真正承诺的范围。**

### 三道扫描闸门

保证：G1 在 plan、G2 在提交前（读**索引 blob**）、G3 在推送前；`--range <rev-range>` 扫的是该范围**新引入的全部 blob**（每个对象只读一次、按对象 id 去重），而不是右端修订上的那份内容 —— 提交 A 加进密钥、提交 B 把文件删掉或改干净时，那个 blob 照样会永久留在远端历史里。`--range` 只接受真正的 rev-range，单个修订被拒绝（exit 2）。

边界：

- **检测能力就等于规则表本身。** 能抓到的只有 `scripts/patterns.tsv` 里那 16 条规则覆盖的形状；一条规则都没覆盖的凭据（自造前缀、纯随机串、藏在图片或二进制里的密钥）不会被任何一道闸门拦下。规则表可以本地扩充，但扩表不会让旧 `PLAN_ID` 失效（见下一条），所以扩完要重新 plan 才有意义。
- **G1 只看 `local` 这一侧。** 它的范围是 `main...local`，即"本地相对镜像新引入的对象"；上游那些还没合入的提交不在里面，它们要等 `apply` 的 G3（`main..local`，或之后的 `origin/local..local`）或兜底闸门才进扫描集。所以"plan 报干净"不等于"这次推送干净"。
- **规则表不是审批凭证的输入。** 进状态哈希的只有扫描器的标准输出，因此把 `patterns.tsv` 改空、改成不可读，或新增一条不会命中任何东西的规则，都**不会**让旧 `PLAN_ID` 失效。规则表坏掉的后果是扫描器变成"不可用"（exit 2），由 apply 的复检以 exit 5 拦下 —— 那条路径才是防线，不是哈希。
- **豁免只有一个：仓库根的 `.sync/*`；它与守卫集逐点一致。** 三道闸门共用的跳过集就是这一项 —— **不是**"任何叫 `.sync/` 的目录"，也**不再**包含规则表 `scripts/patterns.tsv`（规则表本身也照扫）。这条收窄是安全要求：`apply.sh` 的两道 `.sync/` 守卫都是**根锚定**的（跟踪集用 pathspec `.sync/`、推送范围只认行首的 `.sync/`），所以跳过集与守卫集现在**逐点相等**：`skills/<x>/.sync/**` 与 `skills/<x>/patterns.tsv` 这类既不扫也不拦的缝已经不存在，落在那两处的凭据都会被照扫命中（回归锚点：`tests/upstream-sync/test-scanner.sh` §11 与 §12）。
  规则表曾经被豁免，理由是"表正文里写着全部正则，将来某条规则可能匹配到规则表文本"。实测这条理由不成立：**今天这张表并不自我命中**（把出厂表逐字节复制到非豁免路径上扫，exit 0、零输出；§12a 是它的回归锚点），而代价是跳过集比守卫集多出一个**没有任何守卫**的成员 —— 写进规则表的凭据会被三道闸门全部跳过。删掉它之后多出一条**有意**的新性质：**若将来有人加一条规则，其正则匹配到它自己那一行定义文本，`--paths skills/upstream-sync` 这条自净检查会立刻响亮失败**（此前那张表每次都被整份跳过，"被跳过"与"干净"不可区分）。那时把规则的写法改成不自我命中即可（用字符类打断字面量，例如写 `mycompany[-]secret` 而不是 `mycompany-secret`），见 `references/recovery.md`。
- **范围扫描看不见一种字节：** 某个 blob 在范围内只有两个名字，一个是跳过清单上的名字（**仓库根** `.sync/` 下的路径，今天这是跳过清单的全部），另一个名字在范围内被删除。实现已把"该不该跳过"看在范围的全名清单上（右端 ACMR 名字 ∪ 对象清单打印的路径），但上面这种组合仍会漏过。
- 非 blob（提交、树、子模块指针）不扫：它们不是文本，且子模块指针的"内容"里带着提交头。
- `--paths` 是文件系统模式，会递归目录；传进来的路径不存在是用法错误（exit 2），绝不判干净。不要把它指向仓库根：那会把 `.git/` 与整棵树一起读一遍 —— 慢，而且给"被扫的东西"里塞进整整一类与仓库内容无关的对象。
- **提交身份是元数据，内容扫描器抓不到。** apply 在推送前打印待推送范围内每个提交的 `%h %an <%ae>`，让人核对 —— 机制报告它，不替你判断它。

### 推送目的地

保证：`apply.sh` 用 `--all` 读 `origin` 与 `upstream` 的**全部** fetch/push URL；读不到 URL 即失败关闭；只要有一条读不出来就拒绝推送。

这段检查**不挂在"这次有没有东西要推"上，也不挂在 `--no-push` 上**：它校验的是远端配置不变量，与本次推送的规模无关，`apply.sh` 里它排在推送范围那一段之前、无条件执行。

边界：比较是把 URL 当字符串（本地路径形态会先物理化，`file://`、裸路径、`/var` 与 `/private/var` 归一），因此**同一个远端仓库的两种写法**（例如 SSH 形态与 HTTPS 形态）不会被判为相同 —— `origin` 若以上游的另一种写法指向上游，这条检查拦不住它。真正的硬保证是上面的第 1 条：`upstream` 的 push URL 是禁用标记。

### 推送触发（"有没有东西要推"）

保证：`apply.sh` 的早退只在**既没有事要做、也没有东西要推**时发生。只要推送范围非空，推送范围与身份报告、G3 复检、`.sync/` 守卫、推送目的地守卫就全部照跑，哪怕这一轮它自己既没有 merge 也没有采纳。

边界：**判据只看本克隆的远端跟踪引用**（`refs/remotes/origin/*`），不是真的去查远端 —— `plan.sh` 只 fetch `upstream`，从不 fetch `origin`。这个克隆的跟踪引用偏旧时（例如 `local` 是在另一个克隆里推上去的），`apply` 会照着旧视图把其实早已发布过的提交再走一遍全部闸门：结果可能是多做一遍检查后成功（幂等、无害），也可能以 5/6 这样的码拒绝。方向是保守的，但那不是"远端真有新东西"。手工直接 `git push` 时，管的只有本地兜底闸门。

### 兜底闸门（pre-push 钩子）

保证：`install-pre-push.sh` 通过 `git rev-parse --git-path hooks/pre-push` 定位钩子（而不是写死 `<repo>/.git/hooks`），装进去的钩子对每个待推送 ref 跑一次 `--range`；安装是原子的（同目录临时文件 + `mv`，权限写死 755），写完后再问 git 一次"git 会执行的就是这个文件吗"。

边界：

- **`--no-verify` 按设计跳过它。** 它是"绕过 apply 手工 push"的兜底，不是对执行者的强制。
- git 把钩子解析到本仓库之外时（linked worktree、共享 hooks 目录、全局 `core.hooksPath`），脚本**拒绝安装**并打印原因和 `config --unset` 命令：闸门没装，但你立刻知道。此时只有 apply 自己的检查在管。
- 钩子固化了本仓库根与扫描器路径，因此只属于这一个仓库。
- 钩子只扫本次推送范围：范围之外的既有命中不阻断。

### 审批凭证

保证：`apply.sh` 重新计算状态哈希并与 `--plan-id` 比对，不一致即 exit 3。哈希输入含分支名、`main` 与 `local` 的 sha、游离技能清单与每个未跟踪文件的 blob 摘要、冲突预演结果、工作区 porcelain 的排序输出、G1 扫描输出。

边界：`.sync/plan.json` 是一份**记录**，不是输入 —— `apply.sh` 从不读它。每次 `plan.sh` 运行都会重写它；运行还没走到产出就失败时（分支守卫、拉取、镜像检查），它会被改写为 `plan_id` 为空、`refused` 为 true。任何"盘上有凭证，所以已经批准"的推理都不成立。

### 代价

边界：`--range` 的成本与本次范围引入的对象数量同阶，**每个 blob 一次读取**（`cat-file blob`，外加一次 `cat-file -t` 判类型）。本仓库实测：**约 37ms/blob**，在 `main...local` 这段范围内约 **9.6 秒**（本机、对象已在本地）。第一次推送一个长期分叉的 fork 会扫很多对象、因而明显比之后的增量推送慢 —— 分叉多长、耗时就有多长（分钟级是常态，不是异常）。`sync_state_hash` 每次调用都会重跑一次范围扫描与一次 `merge-tree`，所以一轮只算一次、两处共用同一个值。

可见性：扫描器在范围扫描的**起止各打一行进度到 stderr**（多少个待查对象、用时多少秒），`apply.sh` 与 `plan.sh` 因为要把扫描输出捕获进拒绝消息、自己另打对应的起止行。这是为了不让"慢"看上去像"卡死"——那种误判正是 `--no-verify` 的入口。stdout 是命中契约，进度一律不走 stdout。`sync_state_hash` 内部那一次扫描是静默的（它只把 stdout 计入哈希、stderr 一律丢弃），`plan.sh` 在进入它之前另打一行说明。

**已知的、尚未开工的优化**：扫描器对每个 blob 各起一次 `git cat-file`（两进程一次 blob）。批量读取（`cat-file --batch`、一次进程读多个对象）本可显著降低成本，但没有做 —— 这个项目已经两次因为改动扫描器的枚举/读取路径引入回归（先是一处 pathname 规则盲点，后是一处目录假阳性），而这套机制正处在收口阶段，不适合再做第三次这样的改动。
