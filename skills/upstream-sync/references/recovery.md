# 失败与回滚（Recovery）

被拒绝不等于出事。这张表先说清每个退出码是什么意思，再说每种失败该做什么、什么可以安全重试、以及怎么退回去。

## 退出码

**`plan.sh`**（不碰工作区、索引与分支）

| 码 | 含义 |
|---|---|
| 0 | 出计划成功（含"没有新提交"这类情形）；最后一行是 `PLAN_ID=<64 位十六进制>` |
| 1 | 运行错误：拉取失败（远端不可达，或上游强推过历史）、缺少本地镜像分支 `main` |
| 2 | 拒绝：不在 `local`（I1）；`main...local` 存在非纯新增路径（I2）；G1 命中或扫描器不可用 —— **不给 `PLAN_ID`** |

`plan.sh` 不使用 3–7。它不是"零副作用"：会拉镜像 ref（`--no-fetch` 可跳过），并写 `.sync/plan.json` 与 `.git/info/exclude` 里的一行；工作区、索引与分支一概不动。

**`apply.sh`**

| 码 | 含义 |
|---|---|
| 0 | 成功落地。有两支：**无需变更**（既没有 merge、也没有待采纳的游离技能、**也没有待推送的提交** —— 什么都没推），或已落地（`--no-push` 之外会打印 `push: 已推送到 origin/local`）。只看退出码分不出这两支，要看输出那一行 |
| 1 | 运行错误：git/IO 读不出来；**推送失败**（远端不可达、权限、网络） |
| 2 | 用法错误（`--plan-id` 缺值、未知选项、`--plan-id` 后跟另一个选项）；不在 `local`（I1）；游离技能数据问题（缺 `SKILL.md`、frontmatter 名字与目录不同名、缺 `description`、含嵌套 `SKILL.md`） |
| 3 | `PLAN_ID` 与当前状态不符（计划过期） |
| 4 | 工作区不干净（`?? skills/…` 这类未跟踪路径除外 —— 按字面前缀放行，不限于待采纳的目录） |
| 5 | 安全闸门：暂存内容或推送范围的敏感信息命中、扫描器不可用；`.sync/` 下有已跟踪文件；推送范围内含 `.sync/` 路径；`upstream` 的 push URL 不是禁用标记；`origin` 的 URL 指向 upstream |
| 6 | 仓库自检失败 |
| 7 | 合入预演存在冲突 |

`scan-sensitive.sh`：`0` 干净、`1` 命中、`2` 用法错误或环境不可用（规则表读不到、路径不存在、枚举与实扫对不上）。**`2` 不是干净。**

`install-pre-push.sh`：`0` 已安装；`1` 拒绝或环境问题（不是 git 仓库、钩子目录在本仓库之外或不存在、钩子路径存在但不是普通文件、建不了临时文件、写完复核失败）；`4` 已存在一个非本机制管理的钩子，拒绝覆盖。

## 失败处置

| 失败 | 行为 | 该做什么 |
|---|---|---|
| 拉取 / 网络失败 | plan 报错退出（1）；它不碰工作区、索引与分支，也没有产出可用的 `PLAN_ID` | 恢复网络或先查 upstream 是否强推过历史；重跑 plan |
| 冲突预演非空 | plan 照常出报告并仍给 `PLAN_ID`（只把冲突逐条列出）；apply 拒跑（7） | 因为只做纯新增，冲突只可能来自 upstream 也新增了同名技能 —— **给你的技能改名**，然后重新 plan |
| `PLAN_ID` 不匹配 | apply 拒绝执行（3） | 重新 plan、重新审阅；不要手工拼哈希，也不要改 `.sync/plan.json` |
| 敏感信息命中 | apply 拒绝执行（5）并列出命中位置 | 改写（首选）、移出仓库、或由本人写白名单；然后重新 plan |
| 扫描器不可用 | 同样以 5 拒绝（`plan.sh` 侧是 2） | 修规则表 `patterns.tsv`（字段数、kind、正则能否编译），再重新 plan |
| 规则表被自己命中（新加的规则匹配到它自己那一行） | 当作普通命中处理：命中位置指向 `skills/upstream-sync/scripts/patterns.tsv`，`--paths skills/upstream-sync` 这条自净检查也会红 | 规则表本身现在**照扫**（跳过集里已经没有它），所以改写那条规则的写法，让它不再匹配自己那一行：用字符类打断字面量（写 `mycompany[-]secret` 而不是 `mycompany-secret`），或把要拦的形状写成不含自身文本的等价写法。改完必须重新 plan。这是**有意**的行为：没有这一条，一张自我命中的表会让每次扫描都被自己挡住，而删除豁免之前那个问题被"整张表永远跳过"掩盖着 |
| `.sync/` 还在**跟踪集**里 | apply 在任何改动之前以 5 拒绝，本地零痕迹 | `git rm -r --cached .sync` + 提交，然后重新 plan。若历史上还提交过 `.sync/`，下一步会撞上下面那一格 |
| `.sync/` 只在**历史**里（先提交、后删除） | 跟踪集检查沉默，由推送范围守卫拒绝（5） | 这一格 `git rm --cached` **帮不上忙**：那批提交仍在推送范围里，重跑只会以同一个码再拒一次。出路只有两条 —— **改写历史**让 `.sync/` 不再出现在推送范围里（`git rebase`，或 `git filter-repo --path .sync --invert-paths`；`local` 是独占分支，改写代价小），或者**不推**这段范围。脚本不会替你改写历史，改写后状态已变，必须重新 plan。**另有一层**：若那批提交**已经在 fork 上**，改写历史之后 `apply` 自己推不上去 —— 它从不 force-push，`git push` 会因非快进而失败并以 exit 1 结束；最后一步只能由人手工 `git push --force-with-lease origin local`，那一次推送**绕过 apply 的全部闸门**，只剩本地 pre-push 兜底闸门在管（`--no-verify` 还能把它也跳过）。用 `--force-with-lease` 而不是 `--force`：它在远端已经不是你上次看到的那个提交时拒绝覆盖，而这个分支的重点正是"别把别人的东西冲掉"。所以事先别把 `.sync/` 提交进去 |
| 工作区不干净 | apply 拒绝执行（4），**绝不 stash、绝不覆盖你的改动** | 由人类伙伴决定：自己提交或自己撤销；脚本不替你决定 |
| 仓库自检失败 | 不 push（6）；改动留在工作区与本地提交里 | 修自检。文案会**按运行时根的实际状态**说清新内容是否已在运行时生效（运行时根是指向本仓库 `skills/` 的符号链接时说"已在运行时可见"，否则说"只在工作区与本地提交里、尚未生效"）；修完必须**重新 plan**，因为 merge/采纳可能已经产生了新提交 |
| push 失败 | 本地提交完好、没有丢失（1） | 先看清这一轮做到哪一步。**这一轮没有产生过 merge/采纳提交**（`apply` 什么都没提交，只是在推你手工提交的东西）时：状态未变，原凭证仍然有效，排除原因后**重跑 apply 即可重试**。**这一轮已经 merge 或采纳过**时：本地已经多出提交，状态与批准时的凭证不再一致，重跑会先卡在审批门（exit 3）—— 必须**重新 plan、重新审阅、拿新凭证**再 apply。两种情形下本地提交都没有丢，也都还没有推送出去；拿不准时看 `git log --oneline <origin/local 或 main>..local` 里有没有这一轮产生的 merge/采纳提交 |
| 合入之后需要整体退回 | 只要还没 push，本地就能退 | 见下面的"回滚：merge 之后、push 之前" |
| 运行时需要彻底退回 | 脚本不代劳，由人执行 | 见下面的"回滚：运行时技能根" |

关于"手工提交"：只要**本克隆的远端跟踪引用**（`refs/remotes/origin/*`）里没有这些提交，`apply` 就会走推送那一程（推送范围、身份报告、G3、`.sync/` 与目的地守卫全跑），哪怕这一轮它自己既没有 merge 也没有采纳。早退（"无需变更"）只在**既没有事要做、也没有东西要推**时发生，两条都满足才会什么都不推。

比的是**这个克隆的跟踪引用**，不是真的去查远端：`plan.sh` 只 fetch `upstream`，从不 fetch `origin`。若 `local` 是在另一个克隆里推上去的，这里的跟踪引用就是旧的 —— 于是 `apply` 会照着旧视图走完闸门，把其实早已发布过的提交也算进推送范围：结果可能是多做一遍检查后成功（幂等，无害），也可能是闸门以 5/6 这样的码拒绝（例如推送范围的扫描命中一段早已公开的历史，或自检失败）。方向是保守的，但要知道那不是"远端真有新东西"。

## 回滚：merge 之后、push 之前

```bash
git log --oneline -3          # 先看清要放弃的是哪几个提交
git reset --hard ORIG_HEAD    # 回到 merge 之前的 local
```

`ORIG_HEAD` 是 merge 时留下的那个提交（采纳提交不会改它），所以这一条会把这次 apply 的 merge 与采纳一起退回去。

边界：如果在这之后又跑过别的 merge / reset / rebase，`ORIG_HEAD` 可能已经指向别处 —— 那时先用 `git reflog` 确认目标再 reset。`--hard` 会丢弃未提交的改动；apply 本身要求工作区干净，所以正常路径上不会有未提交的东西可丢。

## 回滚：运行时技能根（由人执行）

这一步动的是运行时目录，脚本不代劳。恢复一次性收敛（M6）时留下的备份：

```bash
mv ~/.dsh/skills ~/.dsh/skills.broken
mv ~/.dsh/skills.bak-<版本>-<日期> ~/.dsh/skills      # M6 建立的备份目录
ls -ld ~/.dsh/skills
```

写法是逐个具名，而不是 `mv ~/.dsh/skills.bak-* ~/.dsh/skills`：后者只在恰好匹配到一个备份目录时才成立。

回退完**开一个新会话**复核技能 catalog —— 技能是在会话启动时发现的，当前会话的 catalog 不会变。

## 不要做的事

- 不要用 `--no-verify` 去绕过兜底闸门。它是为人留的逃生门，不是给流程留的捷径。
- 不要为了通过 exit 4 而 `git stash`。拒绝的原意就是不覆盖你的改动，把改动藏起来只是把问题推到后面。
- 不要手工修改 `.sync/plan.json`、手工拼 `PLAN_ID`，或把旧报告里的 `PLAN_ID` 拿来复用。
- 不要为了消除冲突而删除技能，也不要改上游拥有的文件 —— 改名是唯一的约定动作。
